# explain Implementation Plan

**Goal:** Eine Erklär-Skill mit zwei Zusagen, die ein normales Gespräch nicht gibt:
Die Kurzantwort steht immer vorn und ist auf jeder Effort-Stufe gleich knapp, und
Unsicherheit wird benannt statt weichgespült.

**Architecture:** Tier 0 — **kein Skript, keine Datei, keine Shell.** Die Skill ist drei
Dateien Doktrin. Das hat eine Konsequenz, die den Bau umbaut: Es gibt keinen Code, den
Unit-Tests prüfen könnten. Das **einzige** Messinstrument sind die Evals. Deshalb werden
sie hier **zuerst** geschrieben, nicht wie bei learning-coach als Task 3 — sie sind die
ausführbare Definition von „fertig", nicht ihre Nachkontrolle. Was kein Eval prüft,
existiert in dieser Skill nur als Absichtserklärung.

**Tech Stack:** Kein Anwendungscode. Einziger Python-Anteil ist ein Schema-Test für
`evals/explain/evals.json` (Vorbild: `tests/test_exercise_forge_evals_schema.py`).

**Spec:** `specs/Spec 15 – explain.md`, gebunden an `specs/Spec 00 – skill-foundation.md`.

## Global Constraints

- **E1 — Tier 0.** Kein Skript, kein Dateizugriff, keine Persistenz. Zielsystem ist
  claude.ai/Cowork; die Skill muss dort vollständig laufen, nicht degradiert.
- **E2 — Portables Frontmatter.** Nur `name` und `description` (Spec 00 §5).
- **E3 — SKILL.md ≤ 150 Zeilen.** Alles Weitere in `references/`. Die Grenze ist hart;
  learning-coach liegt exakt darauf und musste dafür einen Abschnitt auslagern.
- **E4 — Marker sind feste Tokens.** `Unverified:` und `Source:`, wörtlich, unabhängig
  von der Antwortsprache. Sie sind der einzige mechanisch prüfbare Teil der Skill —
  jede Abweichung im Wortlaut macht Eval 3 und 4 wertlos.
- **E5 — Gate-Ehrlichkeit (Spec 00 §4).** Alles hier ist **G1 (Selbstauskunft)**:
  Die SKILL.md *verlangt*. Kein Text in SKILL.md oder References darf „blockiert",
  „erzwingt" oder „stellt sicher" behaupten — es gibt nichts, was das einlösen könnte.
- **E6 — Anti-Zeremonie ist Pflicht** (Spec 00 §2) und hier besonders scharf: Eine
  dreiteilige Antwortform ist genau die Art Struktur, die den trivialen Fall aufbläht.

## Skill-Struktur

```

├── SKILL.md               (Antwortform, Effort-Tabelle, Ehrlichkeitsregeln, Abgrenzung)
└── references/

    └── effort-ladder.md   (fünf Stufen, je beobachtbar definiert)

evals/explain/evals.json
evals/fixtures/ex-*/       (nur falls Fixtures überhaupt gebraucht werden — siehe Task 1)
tests/test_explain_evals_schema.py
```

## Task 1: Evals zuerst

Die Evals definieren, was die Skill schuldet. Sie entstehen vor jeder Zeile Doktrin.

- [ ] Vor dem Schreiben klären, was der Harness kann: `evalkit/schema.py` gibt jedem
      Eval **einen** `prompt`. Jeder Spec-Eval, der zwei Läufe vergleicht (low vs. max,
      deutsch vs. englisch), muss deshalb in **zwei Evals mit je einer Assertion**
      zerlegt werden — nicht in einen Eval mit einem zusammengesetzten Judge-Claim
      (`docs/known-limits.md`, Abschnitt „Judge": zusammengesetzte Claims sind
      nachweislich unzuverlässig).
- [ ] Klären, ob eine Tier-0-Skill überhaupt eine Fixture braucht. Wenn `fixture`
      optional ist und keine Datei geprüft wird: ohne Fixture fahren und das in `notes`
      begründen, statt eine leere Fixture als Dekoration anzulegen.
- [ ] **Eval `anti-ceremony-trivial-question-stays-short`** (Pflicht, Spec 00 §2):
      triviale Frage mit `low`. Assertion mechanisch, nicht als Stimmungsurteil —
      bevorzugt eine harte Obergrenze auf die Ausgabelänge, sonst ein Judge-Claim mit
      *einer* entscheidbaren Bedingung. Kein weicher Claim, den auch eine geschwätzige
      Antwort besteht.
- [ ] **Eval `short-answer-stays-short-at-max`**: dieselbe Frage mit `max`. Prüft Teil 1
      isoliert. Zusammen mit dem vorigen Eval bildet er den low/max-Vergleich ab, ohne
      dass ein einzelner Eval zwei Läufe braucht.
- [ ] **Eval `uncertainty-is-marked-not-hedged`**: Frage nach einem Detail hinter dem
      Wissensstand, mit `low`. `output_matches` auf `Unverified:`. Die Frage muss so
      gewählt sein, dass Unsicherheit **reproduzierbar** entsteht (etwas nachweislich
      Zeitabhängiges), nicht zufällig.
- [ ] **Eval `high-effort-researches-and-cites`**: dieselbe Frage mit `high`.
      `output_matches` auf `Source:`.
- [ ] **Eval `marker-token-is-language-independent`**: dieselbe Frage auf Englisch,
      `output_matches` auf denselben Token.
- [ ] **Eval `codebase-question-is-routed-away`**: „erklär mir die Architektur von
      diesem Projekt" — `explain` übernimmt nicht, sondern verweist. Judge, ein Claim.
- [ ] `evals/explain/evals.json` gegen `evalkit.schema.load_evals` validieren.
- [ ] Commit.

## Offene Punkte, die vor Task 2 entschieden werden müssen

**Wann trägt eine Aussage keinen Marker?** Die Spec regelt, was `Unverified:` und
`Source:` bedeuten, aber nicht den Normalfall. Wenn jede Aussage einen Marker braucht,
ist die Antwort unlesbar; wenn nur „unsichere" einen brauchen, hängt alles an genau der
Selbsteinschätzung, die die Spec selbst als schwächste Stelle benennt. Vorschlag zur
Entscheidung in Task 2: Marker sind **satzweise und nur bei Bedarf** — die Kurzantwort
(Teil 1) trägt nie einen, weil sie per Contract nur Gesichertes enthalten darf; ist
nichts Gesichertes da, sagt Teil 1 genau das. Damit wandert die Last vom Erkennen von
Unsicherheit auf eine Regel über Teil 1, die schärfer ist.

**Anti-Zeremonie vs. dreiteilige Form.** Ob Teil 3 (Anschluss) bei `low` entfällt,
entscheidet Eval 1 — aber die Entscheidung muss *vor* dem Schreiben von SKILL.md
fallen, sonst steht sie zweimal verschieden in den Dateien.

**Reviewbefunde.** Ein unabhängiger Subagent-Review der Spec läuft; seine Funde werden
vor Task 1 eingearbeitet. Was er an Widersprüchen findet, gilt gegenüber diesem Plan
als vorrangig.
